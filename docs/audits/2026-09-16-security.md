## Hallazgos

### 1. P1 - La cookie privada no permite revocacion individual inmediata

- Estado 2026-09-16: corregido en el arbol local. Se agrego `private.panel_sessions`, RPCs service_role para crear/validar/revocar, cookie con `sid + secret`, validacion de sesion activa en panel/transporte y revocacion al cambiar clave. Pendiente aplicar `supabase/migrations/20260916170000_panel_server_sessions.sql` y desplegar.
- Evidencia: src/lib/panel/auth.ts:88-141, src/lib/transport/access.ts:43-64 y src/lib/server/panel-session-cookie.ts:62-85.
- La cookie guarda identidad/email/expiracion y firma HMAC, pero no un identificador de sesion verificable. Las peticiones con cookie no consultan el estado actual del usuario ni de su sesion. El fundador accede antes de consultar membresias.
- Una copia valida de la cookie sigue autorizando hasta expirar aunque se cierre globalmente la sesion. Borrar la cookie del navegador propio no invalida copias. La ventana depende del exp del token original, no necesariamente de siete dias.
- Ademas, src/components/panel/UpdatePasswordForm.tsx:134-137 limpia storage y ejecuta signOut, pero no llama clearPanelServerSession: deja la cookie incluso en el navegador que acaba de cambiar la clave.
- Reproduccion offline original: una cookie de fundador valida autorizaba sin ninguna consulta al servicio de identidades. Reproduccion actualizada: una cookie firmada se rechaza si falta la sesion del servidor o esta revocada. No se robo ni reutilizo una cookie real.
- Correccion: sesion servidor revocable (session_id/version y validacion de estado) y borrar cookie al cambiar clave. Cubrir cierre global, bloqueo y eliminacion del usuario. getUser por si solo no demuestra revocacion global de una sesion.

### 2. P2 - Registro con correo ajeno de una cuenta huerfana

- Estado 2026-09-16: corregido en el arbol local. Si el correo ya existe, solo se reutiliza el usuario cuando hay `oauthAccessToken` validado y el `user.id` coincide. Sin prueba de identidad devuelve conflicto. El fallback posterior a `signUp` solo recupera usuarios creados en la misma ventana breve de solicitud.
- Evidencia: src/app/api/signup/route.ts:293-306 y src/app/api/transport/agencies/apply/route.ts:174-191.
- Si el correo ya existe pero no tiene membresias, se reutiliza su user_id sin exigir token OAuth ni comprobar la clave enviada. Solo se comprueba la longitud de la clave cuando falta OAuth.
- Consecuencia: un tercero que conoce ese correo puede crear un comercio o solicitud delivery en nombre de la victima y ocupar el alta pendiente. No se demostro toma de cuenta ni acceso a comercios ya vinculados; estos se rechazan.
- La reproduccion ejecuta ambos handlers reales con dependencias simuladas: respuesta exitosa y escritura de membresia para victim-user, cero verificaciones de identidad. El caso cobra relevancia con usuarios que abren Google y abandonan antes de completar el registro.
- Correccion: exigir identidad autenticada y coincidente para recuperar cualquier cuenta existente; sin ella, responder conflicto y pedir iniciar sesion. Revisar tambien recuperacion posterior a signUp y condiciones de carrera.

### 3. P2 - Redireccion externa despues de iniciar sesion

- Estado 2026-09-16: corregido en el arbol local. `LoginForm` y el retorno OAuth usan `safeInternalPanelPath`, que rechaza rutas sin slash inicial, doble slash, barra invertida, caracteres de control y destinos cuyo origin no coincida.
- Evidencia: src/components/panel/LoginForm.tsx:42-43 y :89-93.
- La validacion de next acepta una barra seguida de barra invertida. El parser URL lo convierte en un destino de otro dominio. El enlace de login puede llevar next=%2F%5Cexample.invalid para demostrar el patron sin usar un dominio real.
- Verificacion offline del predicado y parser; la implementacion instalada de Next construye new URL(href, location.href) y permite navegacion externa (app-router-instance.js:219-228 y navigate-reducer.js:34).
- Consecuencia: despues de autenticar, el usuario puede acabar en una pagina ajena, util para phishing. No se demostro transferencia de tokens al destino. No se hizo login con cuentas reales para explotar el caso.
- Correccion: resolver URL y exigir el mismo origin y rutas internas permitidas; rechazar barras invertidas y caracteres de control. Reutilizarlo para next y retorno OAuth.

### 4. P3 - Mensajes internos devueltos al panel

- Estado 2026-09-16: corregido en el arbol local. `panelErrorResponse` ya no devuelve `error.message` de errores desconocidos; solo conserva `PanelAccessError` y mensajes de negocio con prefijos permitidos. El resto usa el fallback generico de cada ruta.
- Evidencia: src/lib/panel/access.ts:94-106 devuelve directamente error.message para errores no controlados, incluidos errores de base de datos.
- Puede revelar nombres de tablas, restricciones o detalles internos a un usuario autenticado que provoque un error. No se demostro filtracion de secretos.
- Correccion: conservar mensajes de negocio mediante errores tipados; registrar detalles en servidor y devolver mensaje seguro con identificador de incidente.
